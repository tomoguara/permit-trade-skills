# Operations runbook

How to run, change, check, back up, and prune the canonical store, and how to
operate the Stage 07 pipeline worker, planner and review ([Orchestration](#orchestration-stage-07)). The schema
itself, with its ER diagram and query cookbook, is in [schema.md](schema.md). For
a high-level architectural overview of the Canonical Data Store and how all
stages interact with it, see the [C4 Component Diagram](diagrams/schema-c4.png)
in the schema documentation.

All commands read the database URL from `--db-url`, else
`PERMIT_TRADE_SKILLS_DB_URL` (shell or `.env`), else the local Docker default
`postgresql://postgres:postgres@localhost:5432/permit_trade_skills`.

## Command reference

| Command | What it does |
|---|---|
| `pts db status` | Current revision, head, pending revisions, and any pending `--destructive` ones |
| `pts db migrate` | Upgrade to head. Refuses destructive revisions unless `--destructive` is given |
| `pts db migrate --destructive [--yes]` | Also applies destructive revisions, after a confirmation prompt |
| `pts db downgrade [-r REV] [--yes]` | Downgrade (default: one revision back). Drops whatever the reverted revisions added |
| `pts db revision -m MSG [--autogenerate] [--rev-id ID]` | Create a migration file (autogenerated = draft to review) |
| `pts db doctor [--sample N]` | Integrity checks; exits 1 on any hard failure |
| `pts db backup [-o FILE]` | Full `pg_dump --format=custom` (default: `backups/<db>-<timestamp>.dump`) |
| `pts db prune [--dry-run]` | Apply the retention policy |
| `pts seeds seattle` | Register or update the Seattle jurisdiction (idempotent; bumps `config_version`) |

Every command that creates tables (`pts seeds`, `pts discover`, `Registry.create_tables()`)
runs `ensure_schema`. That function upgrades to head, but it never applies destructive revisions.

## First run on an existing database

Databases created before Alembic was adopted (by SQLAlchemy `create_all`) have
the tables but no `alembic_version`. `pts db status` reports this as
`none - pre-Alembic schema`. `pts db migrate` stamps such a database at the
`0001_initial` baseline, which reproduces that schema exactly, without touching
data. It then applies the later revisions.

## Changing the schema (models first, then a reviewed migration)

1. Edit the models in `src/permit_trade_skills/discovery/registry.py`. They are
   the only place schema intent is declared.
2. Draft a revision: `pts db revision --autogenerate -m "skill inference audit" --rev-id 0004_skill_inference_audit`.
3. Review and edit the draft in `src/permit_trade_skills/db/migrations/versions/`:
   - Add what autogenerate can't detect: `CREATE EXTENSION`, CHECK constraints
     on existing tables, partial and expression indexes, `FILLFACTOR`, and
     generated columns.
   - Give every constraint and foreign key an explicit name, so `downgrade()` can drop it.
   - Write and check `downgrade()`, including dependency order and data-loss paths.
   - Order operations as extensions, then tables (in FK order), then indexes last.
   - Use plain `op.create_index` at Phase 1 volumes. Switch to
     `CREATE INDEX CONCURRENTLY` (in an autocommit block) only for tables that take
     writes during the migration.
4. Run the round trip locally:
   `pts db migrate && pts db downgrade --yes && pts db migrate && pts db doctor`.
5. `pytest`. `tests/integration/test_migrations.py` checks for a single head,
   a fresh upgrade, the one-step and base↔head round trips, and that the
   models match the migrated schema.

The chain is append-only: never edit or reorder an applied revision.

## Destructive changes

A revision that drops a table or column, or narrows a type, must contain a
docstring line that is exactly:

```
--destructive
```

`pts db migrate` (and `ensure_schema`) then refuse to apply it. To proceed:

1. Back up: `pts db backup`.
2. Apply: `pts db migrate --destructive`. You'll be asked to confirm; `--yes` skips the prompt, for automation.

Downgrades are inherently destructive, since they drop what the reverted
revisions added, so `pts db downgrade` always asks for confirmation unless `--yes` is given.

## Backup and restore

```bash
pts db backup                      # backups/permit_trade_skills-YYYYmmdd-HHMMSS.dump
pg_restore --clean --if-exists -d "$PERMIT_TRADE_SKILLS_DB_URL" backups/<file>.dump
```

`pts db backup` needs the PostgreSQL client tools (`pg_dump`) on `PATH`. The
`backups/` folder is git-ignored. A full dump of the Seattle data (~193k
permits with embeddings) is about 430 MB.

## Integrity: `pts db doctor`

| Check | Severity | Meaning |
|---|---|---|
| `orphan_status_history` | hard | history rows whose permit is gone (FK bypassed, e.g. by a bad restore) |
| `raw_hash_mismatch` | hard | `raw_hash` ≠ recomputed hash of `raw_row` on a random sample (default 1000). A data-corruption alarm |
| `duplicate_permit_number` | hard | the same permit number twice in a jurisdiction |
| `jurisdiction_slug_mismatch` | hard | `permits` / `sync_metadata` rows whose `jurisdiction_slug` ≠ `jurisdiction_id` (see below) |
| `missing_audit_column` | hard | a table without `created_at`/`executed_at`/`changed_at`/`started_at`/`fetched_at` |
| `issued_without_issued_at` | warn | `status = 'ISSUED'` but no `issued_at` (report-only) |
| `schema_not_at_head` | warn | pending migrations |

The command exits 1 if any hard check fails, so it can gate CI.

### Repairing `jurisdiction_slug_mismatch`

Before 2026-11-09, `pts sync sync -j <prefix>` (e.g. `-j seattle`) stored the
typed prefix as `jurisdiction_slug`, so
slug-based queries miss those rows. Sync now always stores the full id. To
repair existing rows (take a backup first; see "Backup and restore"):

```sql
BEGIN;
UPDATE permits       SET jurisdiction_slug = jurisdiction_id WHERE jurisdiction_slug <> jurisdiction_id;
UPDATE sync_metadata SET jurisdiction_slug = jurisdiction_id WHERE jurisdiction_slug <> jurisdiction_id;
COMMIT;
```

Then run `pts db doctor` again.

## Retention: `pts db prune`

| Data | Policy |
|---|---|
| `permits.raw_row` | kept forever (audit and eval-replay substrate) |
| `detail_snapshots.raw_html`, `raw_responses` | set to NULL after 90 days (`--raw-html-days`); `content_text`, `fields` and `signals` are never pruned |
| `skill_inferences` | kept forever |
| `sync_metadata` | only the latest 512 runs per jurisdiction are kept (`--keep-runs`) |
| `status_history` | kept forever (append-only audit) |
| `nlu_cache` | rows past `expires_at` (24h TTL) are deleted |

Run `pts db prune --dry-run` first to see the counts. Schedule it daily, for example with cron.

## Vacuum and bloat

- Autovacuum defaults apply.
- `permits` uses `FILLFACTOR=90`, because status and lifecycle updates churn rows.
  The setting only affects newly written pages. To repack existing ones, run
  `VACUUM FULL permits` in a maintenance window: it takes an exclusive lock and
  rewrites the table.
- `status` is part of the hot-path index, so status changes are not HOT updates.
  The fillfactor mainly helps lifecycle and metadata updates.
- `tests/integration/test_store_lifecycle.py` churns 10k status updates twice,
  with VACUUM in between, and asserts the heap stays within about 2× its packed size.
- To inspect bloat: `SELECT n_live_tup, n_dead_tup, last_autovacuum FROM pg_stat_user_tables WHERE relname = 'permits';`

## Partitioning escape hatch (not enabled)

Phase 1 is a single-tenant database. `jurisdiction_slug` is on every permit
row, so the table can later be partitioned (monthly `PARTITION BY RANGE
(issued_at)` per jurisdiction) without changing queries. It would ship as a
`--destructive` revision behind a feature flag.

## CI

The development CI (GitLab CI, not included in this repository) runs two jobs
against a `pgvector/pgvector:pg18` service; the same commands work in any CI:

- `schema-round-trip`: runs `pts db migrate` on a fresh database, then
  `pts db downgrade --yes`, `pts db migrate`, and `pts db doctor`. It runs when
  models, migrations, or `store/` change, and on scheduled pipelines. Schedule
  one pipeline quarterly as the deep-history check.
- `tests`: runs `pytest`, which includes the 200k-row hot-path test, a full
  base↔head round trip, and the Stage 08 harness, gate, judge and drift tests
  on fixtures (among them the check that a cached H2 re-run makes no LLM call).

Tests use the disposable `permit_trade_skills_test` database
(`PTS_TEST_DB_URL`) and refuse any database whose name doesn't end in `_test`.

## Query API (Stage 04)

- Run: `pts api serve --host 0.0.0.0 --port 8000` (uvicorn on
  `permit_trade_skills.server:create_app`). Health check: `GET /health`.
- LLM provider for natural-language queries: `llm.use_local_ollama_model` in
  `config/settings.yaml` (Ollama at `http://localhost:11434` when `true`, OpenAI
  when `false`; `PTS_USE_LOCAL_OLLAMA_MODEL` overrides). If the provider is down,
  `POST /api/v1/query` returns 503 `NLU_UNAVAILABLE`; the structured endpoints keep working.
- Logs are one JSON object per line on stdout: `http.request` (method, path,
  status, duration, `trace_id`), `query.*` (executed query, counts, permit
  numbers) and `llm.complete` (model, prompt version, input/output hashes, tokens,
  cost, latency). Join them on `trace_id` to replay a request.
- Rate limiting: the in-process limiter (`api.rate_limit_per_minute`, default
  60 per client IP) is per process. Behind a load balancer or with several
  workers, rate-limit at the gateway and set the in-process limit to 0.
- Load test: `uv run python tests/load/run_load.py` (200k-row fixture in the
  disposable `permit_trade_skills_load_test` database); results in `docs/api.md`.
- Cookbook, error codes and behavior spec: `docs/api.md`.


## Orchestration (Stage 07)

How the planner, the worker and review work is in
[orchestration.md](orchestration.md). This section is the runbook.

### From a clean repository: a dry run and one agent goal

```bash
./script/pgvector.sh --start
uv run pts db migrate                         # includes 0008_orchestration
uv run pts seeds seattle
uv run pts sync sync -j seattle-kingcounty-wa --local-file data/wa-seattle-building-permits.json
uv run pts pipeline run --dry-run --limit 10  # the plan: no LLM, no network, no writes
uv run pts agent goal "Seattle: permits ISSUED last 90 days, Residential, cost >= 25000 — top 5 by cost, and the trade skills for each"
```

The goal needs an LLM (local Ollama by default; role `agent.planner` in
`config/settings.yaml`) and fetches detail pages for the permits it infers.
`pts agent goal --json` prints the full `AgentReport`; exit code 3 means the
integrity check failed.

### Daily cadence

Sync first, then the worker, then review:

```cron
# m h dom mon dow  (repository directory, uv on PATH)
15 2 * * *  cd /srv/permit-trade-skills && uv run pts sync sync -j seattle-kingcounty-wa >> logs/sync.log 2>&1
45 2 * * *  cd /srv/permit-trade-skills && uv run pts pipeline run --limit 200 --workers 4 --max-minutes 60 >> logs/pipeline.log 2>&1
```

A run that stops (time budget, SIGTERM) leaves the rest queued; the next run
continues. A run is safe to repeat: inferences are cached per input, and
nothing is fetched twice within `detail.min_snapshot_age_hours`. Exit codes:
1 if the run failed or recorded an illegal transition.

Check a run, and the cohort:

```bash
uv run pts pipeline status                          # recent runs
uv run pts pipeline status --run pipeline-20261110T194512-29e87b
uv run pts pipeline status --since 2026-11-01       # counts by state, failure reasons, p50/p95 step latency
```

### Stopping

| Signal | Effect |
|---|---|
| `--max-minutes` reached | Stops scheduling; in-flight permits finish; status `stopped` (`max_minutes`) |
| SIGTERM / SIGINT (Ctrl-C) | Stops scheduling; in-flight permits get `drain_s` (30 s), then are cancelled and keep their state; status `stopped` (`SIGTERM`) |

An LLM call already in flight cannot be interrupted, so after the drain the
process exits when it returns (at most `llm.timeout_s`, 120 s). Under systemd,
set `TimeoutStopSec=180`.

### Retries and backoff

| Attempt | When | After a retryable failure |
|---|---|---|
| 1 | the run that picks the permit up | wait 30 s, then attempt 2 in the same run |
| 2 | same run | `retry_backlog.next_retry_at` = now + 2 min |
| 3 | the first run after that | exhausted: the permit stays `DETAIL_FAILED` / `SKILLS_FAILED` |

Non-retryable failures are not retried. A detail failure (`HUMAN_GATE`,
`REDIRECT_BLOCKED`, `NOT_FOUND`) moves the permit to `SKILLS_SKIPPED` with the
reason in `state_error`. An inference failure (`GROUNDING_FAILED`, `NO_SKILLS`)
stays `SKILLS_FAILED`. To try an exhausted or skipped-by-backoff permit again,
name it: `pts pipeline run --permit <number>` ignores the backlog. To list
exhausted permits:

```sql
SELECT p.permit_number, b.stage, b.attempts, b.last_error->>'error' AS error, b.updated_at
FROM retry_backlog b JOIN permits p ON p.id = b.permit_id WHERE b.exhausted ORDER BY b.updated_at DESC;
```

### Cost controls

- The worker processes at most `--limit` permits per run (default 25): one
  inference call each (a schema retry adds one). The 190k-permit backlog is
  never processed by default.
- `pts pipeline run --dry-run` prints the most LLM calls the run can make.
- Each run report has `llm_calls`, `tokens` and `est_cost`. The cost comes
  from `llm.providers.<profile>.prices` (USD per 1M tokens); local Ollama
  costs 0. A model with no price shows the cost with a `+` (incomplete).
- The planner is capped at 12 turns, 10 tool calls and 4 inferences per goal
  (`orchestration.agent`).

### Review

```bash
export PTS_REVIEWER="Dana Smith"              # or put it in .env; required for decisions
uv run pts review list --confidence low
uv run pts review inspect -p 7145215-CN
uv run pts review approve -p 7145215-CN
uv run pts review reject -p 7123326-CN --note "electrical scope missing"
uv run pts review approve --all --confidence high          # prints the list; changes nothing
uv run pts review approve --all --confidence high --yes    # approves exactly that list
```

Agents never set `PTS_REVIEWER`; the planner's `submit_review` only flags
inferences `NEEDS_HUMAN` (`pts review list --needs-human`).

### Adding a tool (`toolset-v2`)

The planner's toolset is frozen at `toolset-v1`. Any change to a tool's name,
parameters or result shape is a new version:

1. In `orchestration/tools.py`, add the tool and a `build_toolset_v2()` that
   returns a `Toolset([...], version="toolset-v2")`. Keep `build_toolset_v1`.
2. Copy `prompts/planner_v1.md` to `planner_v2.md` if the prompt changes, and
   bump `planner.PROMPT_VERSION`.
3. Point `wiring.agent_toolset()` at v2.
4. Add an offline test in `tests/unit/test_planner_loop.py` (scripted planner,
   `tests/agent_fakes.py`).

Each `agent.start` event records the run's `toolset_version` and prompt
version, and each `tool.call` event its exact arguments (`params_json`).
`pts agent replay` replays those arguments, and reports a call to a tool that
is no longer in the current toolset as skipped.

### Retention

`orchestration_events` grows by roughly 6 rows per permit per run and about 2
per planner tool call. `pts db prune` does not prune it yet. To delete old
events by hand:
`DELETE FROM orchestration_events WHERE created_at < now() - interval '180 days';`
